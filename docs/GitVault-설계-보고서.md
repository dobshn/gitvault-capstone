## [설계 보고서] GitVault: Git 내부 구조 기반 클라이언트 측 암호화 스토리지 아키텍처

### 1. 개요 (Overview)

본 문서는 클라우드 스토리지(Dropbox 등)를 신뢰할 수 없는 저장소(Untrusted Storage)로 가정하고, 클라이언트 측에서 데이터의 **기밀성(Confidentiality)** 과 **무결성(Integrity)** 을 보장하기 위한 아키텍처인 **'GitVault'(Git + Vault)** 의 설계 원칙을 기술한다.

---
### 2. 핵심 데이터 모델 (Data Models)

GitVault는 파일 시스템을 다음 3가지 암호화된 객체로 변환하여 클라우드에 평평하게 저장한다.

1. **Blob (파일 데이터):**
	- 실제 파일 내용을 암호화한 데이터 덩어리.
	- 파일명이나 메타데이터는 포함하지 않으며, 저장된 암호화 객체(`IV || ciphertext`)의 SHA-256 해시값으로 식별된다.
2. **Tree (디렉토리 정보):**
	- 특정 디렉토리에 포함된 파일명과 해당 파일의 Blob 해시값 매핑 정보를 담은 목록.
	- Tree 목록 자체도 암호화되어 상위 Tree에 포함될 수 있다.
3. **Commit (스냅샷):**
	- 특정 시점의 최상위 루트 Tree의 해시값과 타임스탬프 등의 메타데이터를 저장.
	- 클라이언트는 이 Commit 객체의 해시값만 로컬에 보관한다.

---
### 3. 상세 프로세스 시나리오 (Walkthrough)

다음과 같은 디렉토리 구조를 암호화하여 클라우드 스토리지에 업로드한다고 가정한다.

```
[예시 디렉토리 구조]

└── vault (Root)
    ├── a.txt
    ├── b.txt
    └── folder
        └── c.txt
```

#### 3.1. 암호화 및 저장 프로세스 (Locking) : Bottom-up

가장 깊은 곳에서부터 상위로 올라가며 해시를 생성한다.

1. **Blob 생성 (파일 암호화)**
	- `c.txt` 내용 암호화 → 해시 생성 (`h_c`) → 클라우드 업로드
	- `a.txt` 내용 암호화 → 해시 생성 (`h_a`) → 클라우드 업로드
	- `b.txt` 내용 암호화 → 해시 생성 (`h_b`) → 클라우드 업로드
2. **Sub-Tree 생성 (하위 폴더 처리)**
	- `folder` Tree 객체의 내용 생성: `[{name: "c.txt", hash: "h_c"}]`
	- `folder` 내용 암호화 → 해시 생성 (`h_folder`) → 클라우드 업로드
3. **Root-Tree 생성 (최상위 폴더 처리)**
	- `vault` Tree 객체의 내용 생성: `[{name: "a.txt", hash: "h_a"}, {name: "b.txt", hash: "h_b"}, {name: "folder", hash: "h_folder"}]`
	- `vault` 내용 암호화 → 해시 생성 (`h_vault`) → 클라우드 업로드
4. **Commit 생성 및 종료 (최종 확정)**
	- `commit` Commit 객체의 내용 생성: `root: h_vault, time: 2025-11-21-15:00:00`
	- `commit` 내용 암호화 → 해시 생성 (`h_commit`) → 클라우드 업로드
	- **핵심:** 클라이언트는 로컬에 `h_commit` 값을 안전하게 저장한다.


모든 파일 데이터는 Blob 객체로 변환되어 클라우드 스토리지에 업로드된다. Blob 객체의 데이터부분은 파일 데이터의 암호화된 값이다.

### 3.2. 복호화 및 검증 프로세스 (Unlocking) : Top-Down & Lazy Loading

사용자가 Vault를 열람할 때, 수 기가바이트의 전체 데이터를 다운로드하지 않는다. 대신 가벼운 지도(Tree)만 먼저 가져와 파일 목록을 보여주고, 실제 파일(Blob)은 사용자가 열 때만 다운로드 한다.

**상황: 사용자가 Vault를 열고 `/folder/c.txt` 파일을 찾아가는 과정**
1. **Commit 객체 확인**
	- 클라이언트는 로컬에 저장된 `h_commit`을 확인한다.
	- 클라우드에서 `h_commit` 파일 이름의 파일을 다운로드한다.
	- 다운로드한 파일의 내용으로 해시를 재계산하여 로컬 값과 일치하는지 확인한다. (불일치 시 즉시 차단)
	- 검증된 Commit을 복호화하여 Root Tree의 해시(`h_vault`)를 얻는다.
2. **구조 탐색 및 목록 표시**
	- **루트 디렉토리 로딩:**
		- 클라우드에서 다운로드한 `h_vault`를 복호화하여 파일 목록을 획득한다.
		- 이때 실제 파일의 내용(Blob)은 다운로드하지 않는다.
	- **하위 디렉토리 진입**
		- 사용자가 화면에서 `folder`를 클릭한다.
		- 클라이언트는 목록에서 `folder`에 해당하는 해시값(`h_folder`)를 클라우드에서 다운로드한다.
		- 클라우드에서 `h_folder` 다운로드 → 복호화 → 파일 목록을 획득하고 화면에 표시한다. (여전히 `c.txt`의 데이터는 다운로드하지 않은 상태)
3. **실제 데이터 다운로드**
	- 사용자가 `c.txt`를 더블 클릭하여 연다.
	- 클라이언트는 목록에서 `c.txt`에 해당하는 해시값(`h_c`)를 클라우드에서 다운로드한다.
	- 다운로드한 Blob의 해시를 검증하고 복호화하여 사용자에게 원본 내용을 제공한다.

## 4. 시스템의 특징 및 장단점

### 4.1. 두 가지 무결성 검사

클라우드 스토리지의 상태를 점검하기 위해, 비용과 목적에 따라 두 가지 검증 모드를 제공한다.

- **Quick Scan (구조 및 존재 검사)**
    - **동작:** `Commit`과 `Tree` 객체만 다운로드하여 구조적 연결(Link)을 검증하고, 실제 파일인 `Blob` 객체는 다운로드하지 않고 클라우드 상에 **존재하는지(Existence Check)** 만 확인한다.
    - **장점:** 파일의 개수에만 비례하므로 매우 빠르다. 파일 유실(Deletion)이나 동기화 누락을 즉시 발견할 수 있다.
    - **한계:** 파일 내부 데이터가 변조되었는지는 확인할 수 없다.
    - **활용:** 앱 실행 시 또는 일일 점검용.
- **Deep Scan (정밀 검사)**
    - **동작:** 클라우드에 있는 **모든 객체(Blob 포함)** 를 다운로드하여 저장된 객체의 해시를 다시 계산하고, 로컬의 기대 해시값과 대조한다.
    - **장점:** 데이터의 단 1비트라도 손상되거나 변조되었는지 완벽하게 잡아낸다 (100% 무결성 보장).
    - **한계:** 전체 데이터를 다운로드하므로 네트워크 대역폭과 시간이 많이 소요된다.
    - **활용:** 월간 정기 점검 또는 침해 사고 의심 시 수행.

### 4.2. 플랫 객체 저장 구조 (Flat Object Storage)

클라우드 상의 저장소는 계층적인 폴더 구조가 아닌, 해시값을 파일명으로 하는 **평평한(Flat) 구조**를 가진다. (Git의 `.git/objects` 구조 차용)

- **구조적 은닉 (Structure Obfuscation):**    
    - 사용자의 로컬에는 `/Vault/folder/c.txt`와 같은 계층이 존재하지만, 클라우드에는 `a1/b2c3d4...`와 같은 알 수 없는 파일들만 나열된다.
    - 공격자는 파일의 이름, 확장자, 폴더 깊이, 파일 간의 관계를 전혀 파악할 수 없다.

## 5. 결론

GitVault는 Git의 내부 구조(Commit, Tree, Blob 객체)에서 영감을 받아 고안된 클라이언트 측 암호화 프로그램이다. 단 1비트의 내용만 변경되더라도 새로운 Commit 객체가 생성된다는 점에 착안해, 로컬 Commit 객체와 클라우드 스토리지를 통해 새롭게 계산된 Commit 객체를 비교함으로써 클라우드 스토리지의 무결성을 검증할 수 있다.

또한 Tree 구조를 활용함으로써 클라우드의 전체 데이터를 다운로드하지 않고 특정 파일에 접근하며, 경로상의 무결성을 검증할 수 있다.

하지만 Vault 전체의 완전한 무결성을 위해선 클라우드에 저장된 모든 Vault 데이터를 다운로드 받아야하는 오버헤드가 불가피하다. GitVault는 대안으로 Blob의 데이터를 제외한 디렉토리 구조, 메타데이터 등을 검증하는 Quick Scan 기능을 제공한다.

다만 GitVault의 신뢰 주축은 Vault를 lock 하는 기기의 로컬에 저장된 `h_commit`이기 때문에, 사용자의 다른 기기에서 Vault에 접근할 때 클라우드의 불신 문제가 다시 생긴다. 따라서 향후 연구를 통해 사용자의 다중 기기 간의 안전한 데이터 교환 방안을 모색해야 한다.

## Appendix

### 해시 알고리즘 선택

Git은 SHA-1 해시 함수를 사용하지만 SHA-1은 현재 보안 취약점으로 인해 사용이 권장되지 않는다. Git도 SHA-256로 전환을 계획하고 있다. 따라서 우리도 SHA-256으로 해시 함수를 사용한다.

### 암호화 알고리즘 선택

객체별(Blob, Commit, Tree)별 암호화 스킴 통일?
-> 모든 객체 동일 알고리즘, 동일 키 암호화

AEAD를 사용해야 할까?

AES-CTR vs AES-GCM
- AES-CTR
	- 입력으로 IV(nonce)만 추가로 받고, 출력은 암호문만 나온다.
	- 기밀성만 제공한다.
- AES-GCM
	- 입력으로 IV, AD를 추가로 받고, 출력으로 tag도 같이 나온다. tag는 보통 16바이트이다.
	- 기밀성에 추가로 무결성을 제공한다.
GCM을 사용하면 10~40% 정도의 성능 오버헤드와, 객체마다 16바이트의 공간 오버헤드를 감수해야 한다. GitVault 시스템에선 Merkle Tree 구조를 통해 이미 무결성을 제공하기 때문에, CTR 모드를 사용하는 것이 합리적이다.

**IV(nonce) 저장 방법**
- 암호화시
	- 객체를 암호화할 때 IV를 랜덤하게 생성한다.
	- 랜덤하게 생성한 IV를 사용해서 객체를 암호화 한다.
	- 암호화된 객체 앞에 IV를 이어붙인다.
	- `IV || 암호화된 객체` 전체를 해시하여 해당 데이터의 이름으로 사용한다.
- 복호화시
	- 데이터의 해시 값으로 데이터를 찾는다.
	- 앞의 IV를 추출한다.
	- 암호화된 객체를 해당 IV를 사용해서 복호화한다.

즉, GitVault에서 객체의 식별자(hash)는 평문이 아니라 저장 표현(`IV || ciphertext`) 전체에 대한 SHA-256이다.

### 키 관리 전략

사용자 비밀번호를 입력받아 KDF를 통해 키를 생성하는 구조
- 장점
	- 키 저장이 따로 필요하지 않다
	- 사용자의 다중 기기간 키 공유가 필요하지 않다
- 단점
	- 키 분실 우려가 있다
	- 무작위 생성보다 보안이 약하다

### 클라우드에 저장되는 파일 구조

Git은 해시된 파일명의 맨 앞 1바이트를 기준으로 디렉토리를 생성해 분할 저장한다. 이를 샤딩(sharding)이라고 한다.

1바이트는 8비트이므로, 총 256개의 디렉토리가 생성된다. SHA 알고리즘의 결과는 균등하게 분포하므로, 파일은 자동으로 256개의 디렉토리에 균등하게 분산된다.

SHA-1의 출력은 160비트(20바이트)이므로, 맨 앞 1바이트는 폴더 명으로, 나머지 19바이트는 파일 명으로 사용된다. GitVault에선 SHA-256을 사용하므로, 출력은 256비트(32바이트)이다. 따라서 맨 앞 1바이트를 폴더 명으로, 나머지 31바이트를 파일 명으로 사용한다.

**Commit 객체의 해시 저장**

파일 탐색의 시작은 Commit 객체로부터 이루어진다. 따라서 로컬에 저장된 Commit Hash가 없더라도 Commit 객체를 식별할 방법이 필요하다. 이를 위해 Vault에 `HEAD` 파일을 두고, 내용으로 Commit 객체의 식별자를 암호화한 값을 저장한다.

우리의 암호화 방법은 AES-CTR이므로 인증이 제공되지 않는다. 따라서 `HEAD`를 암호화할 때는 MAC을 추가하거나 AEAD 암호화를 사용하여 무결성도 보장한다.

### Packfile 전략 도입 여부

Packfile이란? 여러 객체 파일들을 하나의 큰 파일로 묶어 저장하는 방식이다. 이를 도입하면 클라우드 스토리지 API 호출 횟수를 줄일 수 있다는 장점이 있지만, 여러 Blob 객체들이 한 파일에 모이기 때문에 업데이트 비용이 증가하고, 일부 tree 객체들만 불러오는 lazy loading이 어려워진다. 따라서 도입하지 않는다.

### Tree / Commit 객체 구조

```c
struct Tree {
  uint8   version;        // 1
  uint32  entry_count;    // 엔트리 개수
  Entry   entries[];      // entry 배열
}
```

```c
struct Entry {
  uint8   type;            // 0=blob, 1=tree
  uint8   flags;           // bitmask: size/mtime 존재 여부
  uint16  name_len;        
  uint8   name[name_len];  // UTF-8 NFC
  uint8   hash[32];        // SHA-256

  // Optional fields:
  if (flags & 0x01) uint64 size;
  if (flags & 0x02) uint64 mtime;
}
```

```c
struct Commit {
    uint8  version;                 // 2
    uint64 commit_time;             // epoch (UTC)
    uint8  root_tree_hash[32];      // SHA-256
    uint8  parent_commit_hash[32];  // 직전 Commit의 SHA-256, 최초 Commit은 모두 0
}
```

Commit V2의 저장 크기는 73바이트이며, 새 Commit은 생성 당시의 기존 `HEAD`를 부모로 기록한다. V1을 포함해 V2가 아닌 Commit은 지원하지 않는다. Quick/Deep Scan은 zero-parent에 도달할 때까지 V2 부모를 따라가며 Commit 객체의 존재, 저장 표현 해시와 포맷을 검증한다.

부모 참조를 유지하기 위해 이전 Commit 객체는 삭제하지 않는다. 현재 구현은 이전 Tree와 Blob까지 모두 보존하지 않으므로, 이 Commit 이력은 계보 검증을 위한 것이며 과거 스냅샷 전체 복원을 보장하지 않는다.
